Deployment and backups

How to run SolarCORE on a server that people reach over the internet, keep it backed up, and bring it back if something goes wrong. The project's docs/ folder has the full guides; this page is the overview.

Choose a platform

Check PostGIS first: it decides the platform. SolarCORE needs PostgreSQL with the PostGIS extension. On the database you plan to use, run:

CREATE EXTENSION IF NOT EXISTS postgis;
SELECT postgis_full_version();
OptionUse whenYou manage
Railway (Docker)The platform offers PostgreSQL with PostGIS. Least server work.Variables, a volume for photos, backups
Linux virtual machineYou want full control, or the platform has no PostGIS.The operating system, PHP, PostgreSQL, the web server, HTTPS, backups

Shared hosting without PostGIS cannot run SolarCORE.

On Railway

  1. Create three things in a Railway project:
    • the app, a service from the code repository (Railway builds the included Dockerfile);
    • a PostgreSQL database with PostGIS;
    • a volume on the app, mounted at /data/photos.
  2. Set the variables on the app service: the production settings below, the DB_* values from the database, and PHOTO_STORAGE_PATH=/data/photos.
  3. Deploy. On every start the container runs the migrations; the log ends with Done. All migrations applied. If a migration fails, the app does not start, so read the error and redeploy.
  4. Add a domain in Railway. HTTPS is provided.
  5. Sign in as admin and set the real password and email (email must already work).
The photo volume is not optional A container's own files are rebuilt at every deploy. Without the volume, every uploaded photo disappears while its database record stays.

On a virtual machine

git clone <repository> /var/www/solarcore && cd /var/www/solarcore
composer install --no-dev --optimize-autoloader
cp .env.example .env      # then fill it in
chmod 600 .env            # readable by its owner only
php scripts/migrate.php   # creates the schema

Point the web server's document root at /var/www/solarcore/public, make the photo folder writable by the web server user, and reload. The project's docs/WEB_SERVER_SETUP.md has ready-made Apache and Nginx configurations.

Production settings

Set everything in Configuration. These differ from a laptop:

APP_URLThe public https:// address, with no trailing slash.
PHOTO_STORAGE_PATHA permanent folder or volume outside public/.
MAIL_DRIVERbrevo on platforms that block mail ports; smtp works on most virtual machines.
LOGIN_EMAIL_CODELeave unset, so codes stay on.
Change the initial administrator password The initial admin password exists in the project's history and must be treated as public. Use a different, strong password on every real server. SolarCORE forces a change at first sign-in.

After deploying: a quick check

  • Sign in, and receive and enter the emailed code.
  • Add an installation with a photo; it appears on the map and the photo opens.
  • Switch the map layers; export CSV, GeoJSON and PDF; import the template.
  • Ask the assistant a question.
  • Sign in as a client and confirm only their installations appear.
  • Open https://your-domain/.env: it must not load.

Backups

TargetValue
How much data may be lostAt most 24 hours (one backup a day).
How long until running againWithin 4 hours. A restore of the data itself takes seconds.
KeptThe last 7 daily and 4 weekly copies, stored off the server.

Two things must be backed up together: the database, and the photo folder, because the database stores only each photo's location. The included script does both, checks that the database copy can be read back, and deletes old copies:

scripts/backup.sh --dry-run   # show what it would do
scripts/backup.sh             # back up now

It writes to backups/daily/ (and backups/weekly/ on Sundays). The machine running it needs PostgreSQL's pg_dump and pg_restore, the same version as the server or newer.

Schedule it every night, for example with cron on a virtual machine:

0 2 * * * cd /var/www/solarcore && scripts/backup.sh >> /var/log/solarcore-backup.log 2>&1

Then copy the backups somewhere else (another machine, cloud storage). On Windows, Task Scheduler can run the script through Git Bash.

Restoring

  1. Stop the app so nobody writes to the database you are replacing.
  2. Create an empty database: createdb -h <host> -U <user> solarcore_restore
  3. Restore the database copy: 
    pg_restore -h <host> -U <user> -d solarcore_restore --no-owner --exit-on-error backups/daily/solarcore-db-YYYY-MM-DD.dump
  4. Restore the photos: 
    tar -xzf backups/daily/solarcore-photos-YYYY-MM-DD.tar.gz -C "$PHOTO_STORAGE_PATH"
  5. Point the app at it (DB_DATABASE) and start it. Sign in, count the installations, open a photo, and check the latest audit entries.

Practise a restore before going live. A backup that has never been restored is a hope, not a backup.

Audit trail retention

SolarCORE never deletes audit entries itself. Once a month, remove those older than two years:

php scripts/purge-audit-logs.php --dry-run   # count only
php scripts/purge-audit-logs.php             # remove, and record the purge

Run the backup first, so the removed entries still exist in that month's backups.

Updating a server

  • Railway: push to the connected branch; Railway rebuilds, and the migrations run on start.
  • Virtual machine: back up, then git pull, composer install --no-dev --optimize-autoloader and php scripts/migrate.php.
